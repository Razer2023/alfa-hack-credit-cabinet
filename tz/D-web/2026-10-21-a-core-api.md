# Подключение веба к API ядра

## Зачем
Ядро уже работает: в нём весь путь заявки от черновика до выдачи, статусы, коды подтверждения, живые события и сторона банка. Веб должен показать это пользователю. Дизайн и каркас `web/` описаны в соседнем ТЗ [2026-10-21-a-core-components.md](2026-10-21-a-core-components.md), это ТЗ — про данные и логику экранов.

## Как запустить ядро у себя
```bash
cd services/core
uv sync
uv run alembic upgrade head && uv run python -m app.seed && uv run uvicorn app.main:app --reload
```
Swagger с примерами всех запросов: http://localhost:8000/docs. Контракт: [contracts/core.yaml](../../contracts/core.yaml).

Демо-логины: `coffee`, `stroy`, `vector` — клиенты; `manager`, `underwriter` — банк. Пароль — `CORE_DEMO_PASSWORD` из `.env.example`.

## Общие правила

1. **Адрес API — относительный `/api/v1`.**
   - В разработке: Vite proxy `/api` → `http://localhost:8000`.
   - В Docker: контейнер `web` (nginx) проксирует `/api/` → `http://core:8000`. Для `/api/v1/stream` обязательно `proxy_buffering off;` и `proxy_read_timeout 1h;`, иначе живые события не дойдут.
   - Так не нужен CORS, а адрес одинаковый везде.
2. **Типы из контракта, не руками:** `npx openapi-typescript ../contracts/core.yaml -o src/api/schema.d.ts` (openapi-typescript, MIT). Контракт поменялся — перегенерировал.
3. **Вход:** `POST /auth/login` → `access_token`, дальше заголовок `Authorization: Bearer <token>`. Токен хранить в `sessionStorage`. Ответ 401 на любой запрос → на экран входа. По `user.role` выбирается интерфейс: `CLIENT` → кабинет клиента, `MANAGER` / `UNDERWRITER` → рабочее место банка.
4. **Ошибки** всегда приходят в формате `{"code": "...", "message": "..."}`. `message` написан для человека, показывай его как есть (`Toast` или текст под полем).
5. **Статусы не хардкодим.** Название и подсказка приходят в `status.title` и `status.hint`. Справочник всех статусов — `GET /reference/statuses`.
6. **Кнопки — по `allowed_actions`.** В каждой заявке есть список действий, доступных пользователю в её статусе. Показывай только эти кнопки:

   | Действие | Кнопка | Запрос |
   |---|---|---|
   | `EDIT` | поля формы | `PATCH /applications/{id}` |
   | `PREFILL` | «Заполнить по ИНН» | `POST /applications/{id}/prefill` |
   | `SUBMIT` | «Отправить» | `POST .../submit/code` → `POST .../submit/confirm` |
   | `PROVIDE_INFO` | «Дополнить» | `POST /applications/{id}/info` |
   | `ACCEPT_OFFER` | «Принять» | `POST /applications/{id}/offers/{offer_id}/accept` |
   | `DECLINE_OFFER`, `CANCEL` | «Отказаться», «Отменить» | `POST /applications/{id}/cancel` |
   | `SIGN` | «Подписать» | `POST .../sign/code` → `POST .../sign/confirm` |
   | `TAKE` (банк) | «Взять в работу» | `POST /bank/applications/{id}/take` |
   | `DECIDE` (андеррайтер) | «Решение» | `POST /bank/applications/{id}/decision` |
   | `REQUEST_INFO` (банк) | «Запросить данные» | `POST /bank/applications/{id}/info-request` |

7. **Живые обновления:** `new EventSource('/api/v1/stream?token=' + token)`, событие `application`. На каждое событие перезапроси заявку из `data.application_id`, если она открыта, и покажи `data.message` в `Toast`. При обрыве браузер переподключается сам и догоняет пропущенное (`Last-Event-ID`). Запасной вариант без SSE: `GET /events?after_id=<последний id>` раз в 2–3 секунды.

## Экраны

### Кабинет клиента
- **Каталог (S1.1).** `GET /products` → карточки с суммами, сроками и ставкой. «Оформить» → `POST /applications {product_code}` → переход в мастер.
- **Мастер заявки (S3.1–S3.4).**
  - Шаг «Компания»: поле ИНН (`MaskedInput`) → `prefill`. Поля из `form.company` показывать с бейджем источника `source`: `EGRUL` → «ЕГРЮЛ», `FNS` → «ФНС», `BANK_ACCOUNT` → «Выписка».
  - Шаг «Кредит»: сумма, срок, цель. Пересчёт платежа — `POST /calc/payment` (с задержкой ~300 мс). Каждое изменение сохранять `PATCH`, черновик переживает перезагрузку (S3.4).
  - Шаг «Отправка»: `submit/code` возвращает `demo_code`. Показывай его прямо на экране подписью «Код из SMS (демо)»: SMS по условиям кейса нет. Ввод — `CodeInput`, затем `submit/confirm`.
- **Список заявок:** `GET /applications`, у каждой — статус и подсказка.
- **Заявка и трекер (S4.5).** `GET /applications/{id}/events` → таймлайн (`Steps`): `to_status` — этап, `message` — текст, `created_at` — время. Обновляется по SSE.
  - `NEED_INFO`: показать `need_info.items[].message` и `need_info.comment`, форму дополнения → `POST /info` (поля `amount`, `term_months`, `purpose`, `extra`, `comment`).
  - `APPROVED`, `COUNTER_OFFER` (S6.1, S6.2): карточки `offers` — сумма, срок, ставка, `monthly_payment`. У контрпредложения кнопки «Принять» и «Отказаться».
  - `REJECTED`: причины из `decision.reasons[].text`.
  - Подписание (S7.1): как отправка — код, затем `sign/confirm`. Финальный экран `ISSUED` — «Деньги зачислены».

### Рабочее место банка
- **Очередь (S4.3).** `GET /bank/applications?status=MANUAL_REVIEW&status=...` и переключатель «Мои» (`mine=true`). Таблица: номер, компания, сумма, статус, `status_changed_at`.
- **Карточка андеррайтера (S5.3).** `GET /bank/applications/{id}`: анкета, `enrichment` (ЕГРЮЛ, ФНС, БКИ), `scoring` (балл, класс риска, `factors`, `reasons`), полная история `GET /bank/applications/{id}/events`. Действия по `allowed_actions`:
  - решение `{result: APPROVE | COUNTER_OFFER | REJECT, amount?, term_months?, rate?, comment?}`. Для контрпредложения нужна сумма или срок;
  - запрос данных `{items: [{field, message}], comment}`.
  - Решение может принять только `UNDERWRITER`; `MANAGER` видит карточку и может запросить данные.
