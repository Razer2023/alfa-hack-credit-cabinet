# Скоринг и кредитное решение (область C)

Сервис отвечает на вопрос «давать ли кредит и на каких условиях». Ядро вызывает его на шаге `SCORING` и получает рекомендацию, балл, факторы для андеррайтера, причины для клиента и предложение.

Скоринг **рекомендует, а решает человек**. Автоматически срабатывают только отказ по стоп-факторам и передача рисковых заявок андеррайтеру. Одобрение и контрпредложение подтверждает сотрудник банка: он может поменять условия, и скоринг проверит, что компания их потянет (S5.4).

| Эндпоинт | Story | Что делает |
|---|---|---|
| `GET /api/v1/products`, `GET /api/v1/products/{code}` | S1.1 | Каталог из трёх продуктов |
| `POST /api/v1/calc/payment` | S3.2 | Аннуитетный платёж, переплата |
| `POST /api/v1/decisions` | S5.1, S5.2, S6.1 | Балльная карта → кредитная политика → рекомендация и оффер |
| `POST /api/v1/offers/check` | S5.4 | Проверка условий, которые вписал сотрудник: продукт, ставка, лимит, DSCR |
| `GET /health` | — | Healthcheck, версия правил |

Контракт: [contracts/scoring.yaml](../../contracts/scoring.yaml), генерируется из кода командой `python -m app.export_docs`.

## Запуск

```bash
uv sync
uv run uvicorn app.main:app --port 8001   # Swagger: http://localhost:8001/docs
uv run pytest -q
```

В Docker сервис называется `scoring` и слушает порт 8000. Ядро переключается на него переменной `CORE_SCORING_MODE=http`.

## Правила — в конфиге, а не в коде

Все числа лежат в двух файлах:

- [rules/products.yaml](rules/products.yaml) — продукты, лимиты сумм и сроков, базовые ставки;
- [rules/scorecard.yaml](rules/scorecard.yaml) — факторы и баллы, классы риска, стоп-факторы, триггеры ручного рассмотрения, параметры платёжеспособности, тексты причин.

Версии обоих файлов уходят в ответ как `model_version` (`scorecard-1.1+products-1.0`) и сохраняются в заявке. По любому решению видно, по каким правилам оно принято. Конфиг проверяется при старте: если в нём ошибка, сервис не запустится, а не примет неверное решение. Папку с правилами можно подменить без пересборки образа (`SCORING_RULES_DIR`).

## Как принимается решение

Порядок повторяет классический кредитный конвейер для МСБ: сначала дешёвые проверки, которые сразу дают отказ, потом оценка риска, в конце расчёт суммы, которую компания может обслуживать.

```
Стоп-факторы ──отказ──▶ REJECT
     │
Условия продукта (мин. сумма) ──▶ REJECT
     │
Триггеры ручного рассмотрения ──▶ MANUAL_REVIEW
     │
Балльная карта → класс риска
     ├─ D ──▶ REJECT
     ├─ C ──▶ MANUAL_REVIEW
     └─ A, B
          │
     Лимит по выручке + DSCR
          ├─ запрос проходит ──▶ APPROVE (запрошенные условия)
          ├─ та же сумма на срок длиннее ──▶ COUNTER_OFFER
          ├─ меньшая сумма на макс. срок ──▶ COUNTER_OFFER
          └─ не тянет даже минимум продукта ──▶ REJECT
```

### 1. Стоп-факторы → отказ

| Условие | Почему |
|---|---|
| Компания не `ACTIVE` в ЕГРЮЛ или в ликвидации | Юрлицу, которое прекращает деятельность, кредит не выдаётся |
| Бизнесу меньше 6 месяцев | Нет истории оборотов, оценить устойчивость нельзя |
| Просрочка в БКИ больше 90 дней | Дефолт по определению Базеля и ЦБ |

### 2. Ручное рассмотрение

Эти сигналы не означают отказ сами по себе, но у них часто есть объяснение, которого нет в данных: техническая просрочка, спор с налоговой, офис в бизнес-центре с сотнями арендаторов. Поэтому решение принимает андеррайтер, даже если балл высокий.

- просрочка 31–90 дней;
- задолженность по налогам;
- адрес массовой регистрации;
- нет данных о выручке или кредитной истории.

### 3. Балльная карта (S5.1)

Балл = 520 + сумма баллов факторов, шкала 300–900, как у бюро кредитных историй. У каждого фактора есть корзины значений с баллами. Это стандартная форма скоринговой карты: её легко объяснить клиенту и аудитору, в отличие от «чёрного ящика».

| Фактор | Корзины → баллы | Логика |
|---|---|---|
| Возраст бизнеса | <1 г. −40 · 1–2 г. 0 · 2–3 г. +20 · 3–5 лет +40 · ≥5 лет +60 | Большая часть малых бизнесов закрывается в первые годы |
| Годовая выручка | <6 млн −20 · 6–20 млн +10 · 20–60 млн +30 · ≥60 млн +50 | Масштаб и запас прочности |
| Макс. просрочка в БКИ | 0 +60 · 1–30 дн. 0 · 31–60 −80 · 61–90 −120 · >90 −200 | Самый сильный предиктор будущих просрочек |
| Действующие кредиты | 0–1 +20 · 2 +10 · 3 0 · ≥4 −30 | Много кредитов — признак кредитования «с кредита на кредит» |
| Долг к выручке | <10 % +40 · 10–25 % +20 · 25–40 % −10 · ≥40 % −60 | Текущая долговая нагрузка |
| Запрошенная сумма к выручке | <20 % +30 · 20–35 % +10 · 35–50 % −20 · ≥50 % −50 | Насколько кредит соразмерен бизнесу |
| Сотрудники | <5 −10 · 5–14 +10 · ≥15 +20 | Устойчивость операционной модели |
| Долг по налогам | нет +10 · есть −40 | Платёжная дисциплина |
| Массовый адрес | нет 0 · да −50 | Риск номинальной компании |

Каждый фактор возвращается андеррайтеру с баллом и значением (`"8,4 г."`, `"11,7 %"`), поэтому видно, из чего сложилась оценка.

| Класс | Балл | Решение | Лимит, доля выручки | Ставка |
|---|---|---|---|---|
| A | ≥700 | автоматически | 35 % | базовая −1 п. п. |
| B | 620–699 | автоматически | 25 % | базовая |
| C | 540–619 | андеррайтер | — | — |
| D | <540 | отказ | — | — |

Ставка зависит от риска (risk-based pricing): надёжный клиент получает скидку.

### 4. Платёжеспособность: лимит и DSCR (S5.2)

Одного хорошего балла мало: компания должна физически тянуть платёж.

- **Лимит** = выручка × доля класса, но не больше максимума продукта.
- **Свободный денежный поток** = 20 % среднемесячного оборота по счёту.
- **Платёж по текущим долгам** ≈ 4,5 % долга из БКИ в месяц (оценка, в БКИ нет графиков).
- **DSCR** = свободный поток / (текущие платежи + новый платёж) ≥ 1,25. Это типовой ковенант банков для МСБ: на каждый рубль платежа должно приходиться 1,25 ₽ свободных денег.

### 5. Контрпредложение вместо отказа (S6.1)

Если запрос не проходит по лимиту или DSCR, сервис не отказывает, а ищет условия, которые компания потянет:

1. **Та же сумма на больший срок.** Минимальный срок из ряда кратных 6 месяцам, при котором DSCR соблюдён. Клиент получает нужные деньги, платёж меньше.
2. **Если не помогает и максимальный срок** — максимальная сумма на максимальный срок продукта, округлённая вниз до 100 000 ₽.
3. **Если и она меньше минимума продукта** — отказ с понятной причиной.

Причины (`reasons`) написаны для клиента человеческим языком, коды — для аналитики и экрана андеррайтера.

### 6. Проверка условий сотрудника банка (S5.4)

Рекомендацию скоринга подтверждает менеджер или андеррайтер, и он может поменять сумму, срок или ставку. Чтобы ручные условия не обходили кредитную политику, ядро отправляет их в `POST /offers/check`. Проверяется то же, что при автоматическом решении:

| Проверка | Код | Уровень |
|---|---|---|
| Сумма в рамках продукта | `AMOUNT_BELOW_PRODUCT`, `AMOUNT_OVER_PRODUCT` | ошибка |
| Срок в рамках продукта | `TERM_OUT_OF_PRODUCT` | ошибка |
| Ставка не ниже базовой минус максимальная скидка за риск | `RATE_BELOW_MIN` | ошибка |
| Сумма не выше лимита по выручке (для классов C и D — лимит класса B) | `AMOUNT_OVER_LIMIT` | ошибка |
| DSCR не ниже 1,25 | `DSCR_TOO_LOW` | ошибка |
| Нет данных для расчёта платёжеспособности | `NO_FINANCIAL_DATA` | предупреждение |

Если сумма не проходит, сервис подсказывает максимальную допустимую на тот же срок (`suggestion`). Пример: менеджер вернул СтройМонтажу запрошенные 10 млн на 12 мес. вместо рекомендованных 6,6 млн на 36. Ответ: «Компания не потянет платёж: DSCR 0,46 при минимуме 1,25», подсказка — 2,6 млн на 12 мес.

Скоринг только сообщает о нарушениях, а можно ли подтвердить условия с ошибкой, решает ядро. В банках андеррайтер вправе отступить от политики с письменным обоснованием, менеджер — нет.

## SLA шага скоринга

| Что | Как обеспечивается |
|---|---|
| Время решения | Расчёт локальный, без внешних вызовов: p50 ≈ 5 мс, p99 ≈ 7 мс на 500 запросах (замер через тестовый клиент). Время этапа «Скоринг» в трекере больше: туда входят очередь фонового обработчика и демо-пауза между шагами (`CORE_PIPELINE_STEP_DELAY_SECONDS`) |
| Сервис недоступен | Ядро ждёт ответ до 5 с (`CORE_EXTERNAL_TIMEOUT_SECONDS`), затем повторяет шаг с нарастающей паузой 2, 4, 8… до 60 с. Заявка не теряется и не уходит в отказ, клиент видит «Проверка занимает больше времени, чем обычно». После рестарта незавершённые заявки подхватываются автоматически |
| Готовность | `GET /health` → 200 с версией правил. Docker healthcheck каждые 10 с, ядро стартует только после того, как скоринг здоров |
| Неверные правила | Конфиг проверяется при запуске (корзины по порядку, все факторы и тексты на месте, у продуктов минимум не больше максимума). С ошибкой сервис не стартует — лучше простой, чем неверное решение |
| Воспроизводимость | Решение — чистая функция от заявки и правил. Версия правил (`model_version`) сохраняется в каждой заявке, поэтому любое решение можно разобрать задним числом |
| Масштабирование | Сервис не хранит состояние, поэтому под нагрузкой достаточно запустить больше экземпляров за балансировщиком |

## Упрощения прототипа

Условия кейса запрещают интеграции с банковскими системами и требуют синтетических данных. Поэтому часть расчётов упрощена, но формат и порядок решения такие же, как в продуктиве.

| Упрощение | Почему | Как в продуктиве |
|---|---|---|
| Веса балльной карты экспертные, а не обученные | Реальной истории выданных кредитов и дефолтов у команды нет | Калибровка логистической регрессией (WoE/IV) по выборке выданных кредитов. Формат карты и API не меняются, обновляется только `scorecard.yaml` |
| Свободный денежный поток = 20 % среднемесячного оборота | Нет управленческой отчётности, только синтетическая выписка | Расчёт по выписке за 12 мес. с учётом сезонности и отчётности (ОСВ, ОПиУ) |
| Платёж по текущим долгам ≈ 4,5 % от суммы долга в месяц | Мок БКИ отдаёт только сумму долга, без графиков | Фактические платежи из кредитного отчёта БКИ |
| Ставка зависит только от класса риска | Нет залогов и поручительств в модели данных | Ценообразование с учётом залога, поручительства, срока и стоимости фондирования |
| Возраст бизнеса — от даты регистрации в ЕГРЮЛ | Других данных о деятельности нет | Плюс давность оборотов по счёту и смена учредителей |
| Без ML и LLM в решении | Эксперты кейса: ML и LLM не дают преимущества в оценке. Балльная карта прозрачна, каждое решение объяснимо клиенту и регулятору | ML-модель как дополнительный фактор карты, когда накопится выборка |
