# Правила командной работы

Эти правила обязательны для всех участников и для ИИ-ассистентов, которые пишут код от их имени (см. [CLAUDE.md](CLAUDE.md)).
Области ответственности: [docs/team/AREAS.md](docs/team/AREAS.md). Первая настройка: [docs/team/GITHUB_SETUP.md](docs/team/GITHUB_SETUP.md).

## 1. Роли

- **Главный разработчик (лид)** — владелец области A и администратор репозитория. Единственный, кто сливает PR в `main`, меняет настройки репозитория, создаёт теги и релизы, приглашает людей.
- **Разработчики** — владельцы областей B, C, D. Пишут код только в своей области и открывают PR. Сами в `main` ничего не сливают.

## 2. Своя область — чужая область

- Правим **только файлы своей области** (папки перечислены в AREAS.md). CODEOWNERS автоматически назначит владельца ревьюером, если PR задел чужую папку. Такой PR вернётся на доработку.
- Нужно что-то в чужой области (поле в API, новый мок, исправление бага)? **Не правим сами**, а пишем ТЗ в `tz/` (раздел 5).
- Общие файлы (`README.md`, `docker-compose.yml`, `.github/`, `contracts/core.yaml`) принадлежат лиду. Изменения в них — тоже через ТЗ в `tz/A-core/`.
- Исключение: найденная опечатка или битая ссылка в документации. Её можно поправить сразу, отдельным маленьким PR.

## 3. Ветки и синхронизация

- `main` защищена: прямой push запрещён, только через Pull Request.
- Одна задача — одна ветка от свежего `main`:
  - `feat/<область>-<story>-<кратко>` — новая функция, например `feat/c-s5.1-scorecard`;
  - `fix/<область>-<кратко>` — исправление, например `fix/d-tracker-reconnect`;
  - `docs/<кратко>` — только документация;
  - `tz/<кому>-<кратко>` — только файл ТЗ;
  - `release/X.Y.Z` — подготовка релиза (только лид).
- Синхронизация — **только `git pull`**: перед началом работы и перед каждым `git push`. Свежий `main` подтягиваем в свою ветку командой `git pull origin main` (это слияние, без rebase).
- **Запрещено:** `git push --force` (и `--force-with-lease`), `git rebase` уже запушенных веток, удаление или пересоздание чужих удалённых веток, `git reset --hard` на общих ветках. Чужие изменения не затираем никогда.
- Ветку после слияния GitHub удаляет сам. Локально её можно удалить: `git branch -d <ветка>`.

## 4. Коммиты и Pull Request

- Коммиты по-русски, в формате **«Область: что сделано»**, со story ID, если он есть:
  - `Скоринг: S5.1 балльная карта с 8 факторами`
  - `Веб: S4.5 трекер обновляется по SSE`
  - `Ядро: переход COUNTER_OFFER → SIGNED`
  - `Интеграции: мок БКИ для трёх демо-компаний`
- Коммит — от своего имени и своей почты, привязанной к GitHub (`git config user.name` / `user.email`).
- PR открываем рано, как **Draft**, как только есть первый коммит: команда видит, кто над чем работает.
- PR маленький: одна история, в идеале до ~400 строк изменений. Большую историю режем на несколько PR.
- Перед тем как снять Draft:
  - заполнен шаблон PR (что сделано, story, как проверить);
  - проходят CI-проверки;
  - локально всё поднимается через `docker compose up`;
  - если менялся контракт API — обновлён файл в `contracts/`, и об этом написано в PR.
- Слияние — только **Squash and merge**, и делает его лид. В `main` один PR = один коммит, история читается как список историй.
- Изменения, заметные пользователю, записываем в `CHANGELOG.md` в раздел «Не выпущено».

## 5. ТЗ для другой области

Когда твоей задаче нужна работа в чужой области:

1. Создай файл по шаблону [tz/_TEMPLATE.md](tz/_TEMPLATE.md):
   `tz/<папка-области>/<ГГГГ-ММ-ДД>-<от-кого>-<кратко>.md`
   например `tz/A-core/2026-10-22-d-nextaction-field.md`.
2. Опиши: что нужно, зачем (какая story), какой результат считается готовым, срочность, пример запроса и ответа, если это API.
3. Открой PR из ветки `tz/<кому>-<кратко>` (в нём только этот файл) и добавь владельца области ревьюером. Папка `tz/` общая: такие PR сливаются быстро.
4. Владелец области меняет `status` в шапке файла: `new → accepted → in_progress → done` (или `rejected` с причиной) и указывает номер PR, где ТЗ выполнено.
5. Пока ТЗ не выполнено, работай на моке или заглушке. Не жди и не делай за другого.

Срочные блокеры (без них ты стоишь) дополнительно пиши в общий чат команды со ссылкой на файл.

## 6. Задачи и доска

- Каждая история из story map — Issue на GitHub с меткой области (`area:A` … `area:D`) и приоритета (`mvp`, `validation`, `not-mvp`).
- Доска GitHub Projects: `Todo → In progress → Review → Done`. Issue закрывается автоматически при слиянии PR, если в описании PR есть `Closes #<номер>`.
- Взял задачу — назначь себя исполнителем (Assignee), чтобы двое не делали одно и то же.

## 7. Ревью

- Каждый PR в `main` смотрит лид. Если PR задевает контракт другой области, его владелец тоже (это делает CODEOWNERS).
- Лид отвечает на PR в течение рабочего дня. Последние двое суток перед дедлайном — в течение 2 часов.
- Замечание ревьюера исправляется новым коммитом в ту же ветку (без force-push), после чего ревьюер повторно одобряет.

## 8. Релизы и дедлайн

- Релизы, теги `v*` и деплой на демо-сервер делает **только лид** и только осознанно, не «заодно».
- Версия для жюри — тег `vX.Y.Z` на коммите в `main`. Коммиты после дедлайна жюри не учитывает, поэтому за сутки до дедлайна в `main` сливаем только исправления (code freeze).
- Порядок выпуска: лид создаёт ветку `release/X.Y.Z` (обновляет CHANGELOG и версию), открывает PR в `main`, сливает его, затем ставит тег. Ветку и тег пушим **отдельными командами**.

## 9. Секреты и данные

- В репозиторий не попадают реальные пароли, токены и ключи. Только dev-значения в `.env.example`, реальные — в локальном `.env` (он в `.gitignore`).
- Только синтетические данные. Никаких реальных ИНН людей, паспортов и выписок, даже «для теста».
- Нашёл секрет в истории — сразу сообщи лиду, не пытайся сам переписать историю.

## 10. Требования кейса, которые касаются всех

- Всё запускается одной командой `docker compose up` на обычном ПК, без доступа к Альфа-Банку и платным API.
- LLM — только с открытыми весами, локально. Основной сценарий должен работать и без ИИ.
- Весь сценарий проходит внутри веб-интерфейса: никаких email, SMS и мессенджеров.
- Версии языка и библиотек зафиксированы lock-файлами. Новую стороннюю библиотеку, модель или датасет вписываем в `THIRD_PARTY_NOTICES` (через ТЗ лиду, если файл не твой).
