# Области ответственности

Продукт поделён на 4 области. У каждой области один владелец, своя папка в репозитории и свой набор историй из User Story Map.
Правило одно: **в чужую область код не пишем.** Если нужно что-то от другой области, пишем ТЗ в `tz/` (см. [CONTRIBUTING.md](../../CONTRIBUTING.md#5-тз-для-другой-области)).

Области общаются только через контракты API в `contracts/`. Каждый сервис можно делать и тестировать независимо, пока соседний ещё не готов: для этого есть моки по контракту.

```
 ┌──────────── D. Веб-интерфейс (web/) ────────────┐
 │  кабинет клиента          рабочее место банка    │
 └───────────────┬──────────────────────────────────┘
                 │ contracts/core.yaml
 ┌───────────────▼──────────── A. Ядро процесса (services/core/) ───┐
 │  заявки, статусы, события, роли, подписание, выдача, очередь     │
 └───────┬──────────────────────────────────────────┬───────────────┘
         │ contracts/integrations.yaml              │ contracts/scoring.yaml
 ┌───────▼──── B. Данные и интеграции ───┐  ┌───────▼──── C. Скоринг и решение ───┐
 │  моки ЕГРЮЛ/ФНС/БКИ/выписки,          │  │  продукты, предоценка, скоринг,      │
 │  проверка полноты, документы, OCR     │  │  кредитная логика, контрпредложения  │
 └───────────────────────────────────────┘  └──────────────────────────────────────┘
```

Статусы заявки (единые для всех областей, владелец — A):
`DRAFT → SUBMITTED → CHECKING → SCORING → MANUAL_REVIEW → APPROVED / COUNTER_OFFER / REJECTED → SIGNED → ISSUED`, ветки `NEED_INFO`, `CANCELLED`.

Обозначения приоритета: 🟩 каркас MVP (делаем сейчас) · 🟧 ждёт валидации (итоги интервью 22.10) · ⬜ не в MVP (только описываем в документации как развитие).

## Если в команде 3 человека

B и C объединяются в одну область «Данные и решение» (один владелец). Из неё в первую очередь выпадают S4.8 (OCR) и S1.3 (LLM), они и так вне MVP.

## Где области стыкуются

| Стык | Кто владелец контракта | Как договариваемся |
|---|---|---|
| web ↔ core | A (`contracts/core.yaml`) | D пишет ТЗ в `tz/A-core/`, если нужен новый эндпоинт или поле |
| core ↔ integrations | B (`contracts/integrations.yaml`) | A пишет ТЗ в `tz/B-integrations/` |
| core ↔ scoring | C (`contracts/scoring.yaml`) | A пишет ТЗ в `tz/C-scoring/` |
| синтетические данные ↔ скоринг | B данные, C правила | Демо-компании должны давать три разных исхода: одобрение, контрпредложение, ручное рассмотрение → отказ |
