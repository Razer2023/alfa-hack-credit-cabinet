# Развитие: что не вошло в MVP

Истории из серой зоны [story map](story-map.md). В прототипе их нет. Ниже — зачем каждая, как она ляжет на текущую архитектуру (A — ядро, B — интеграции, C — скоринг, D — веб) и что мешает сделать её сейчас.

Общие ограничения кейса сохраняются: всё работает в `docker compose` без платных сервисов и доступа к системам банка, LLM — только открытые веса и локально, основной сценарий работает без ИИ, весь путь клиента — внутри кабинета.

## Новые по итогам интервью

### S3.6 NEW. Несколько юрлиц и источников дохода в одной заявке (J10)

**Зачем.** У предпринимателя бизнес часто разнесён по ИП и одному-двум ООО, а выручка — по нескольким счетам. Если считать только заявителя, банк видит часть бизнеса, режет сумму или отказывает. Клиенту важно показать полную картину бизнеса (J10).

**Как встроить.**
- **A.** У заявки появляются участники: `application_participants` (компания, роль — заёмщик, созаёмщик, поручитель). Мастер подачи и подписание кодом проходят по каждому участнику: согласие на запрос в БКИ и подпись дают все. В журнале — события по каждому участнику.
- **B.** Профиль, проверки и выписка запрашиваются по каждому ИНН (существующий `/profile` вызывается в цикле). Новая проверка — связанность компаний по ЕГРЮЛ (общие учредители или руководитель). Без связи участник не принимается.
- **C.** Консолидированная выручка и денежный поток группы. Обороты между компаниями группы исключаются, иначе одна выручка посчитается дважды. Стоп-факторы проверяются по каждому участнику, DSCR и лимит — по группе. В ответе `decide` — разбивка по участникам, чтобы андеррайтер видел, откуда сумма.
- **D.** Шаг «Ещё компании и доходы» в мастере: добавить ИНН, выбрать роль, увидеть подтянутые данные. В карточке банка — вкладки по участникам и итог по группе.

**Почему не сейчас.** Нужна модель группы в данных, синтетические связанные компании с перекрёстными оборотами и правила консолидации, которые надо согласовать с рисками. Это меняет контракты всех четырёх областей.

### S6.4 NEW. Альтернатива: лизинг, факторинг

**Зачем.** Кредит подходит не всем. Если клиенту нужна техника, банку проще дать лизинг (предмет остаётся залогом). Если деньги застряли в отсрочке платежа у покупателей — факторинг. Сейчас отказ или маленькое контрпредложение — тупик. Альтернативный продукт сохраняет клиента.

**Как встроить.**
- **C.** В каталоге — продукты другого типа (`type: LEASING | FACTORING`) со своими правилами допуска. Лизинг предлагается для цели «Оборудование» (уже есть в `products.yaml`) и новой цели «Транспорт». Факторинг — при регулярных поступлениях от одних и тех же покупателей в выписке. В ответе `decide` появляется `alternatives`: продукт, почему подходит, ориентировочные условия.
- **A.** Передаёт `alternatives` в `decision` заявки без изменения статусной модели. Переход на альтернативу — новая заявка на другой продукт с данными из текущей (как «Подать снова»).
- **B.** Для факторинга — список покупателей и средний срок оплаты из синтетической выписки.
- **D.** В блоке отказа (S6.3) и рядом с контрпредложением — «Другие способы получить деньги» с кнопкой «Оценить шансы» (предоценка S2.1).

**Почему не сейчас.** Лизинг и факторинг — отдельные продукты со своей логикой риска: предмет лизинга, оценка дебиторов, договор уступки. Без этого альтернатива была бы рекламой, а не решением.

### S5.5 NEW. Учёт контракта и управленческой отчётности (J10)

**Зачем.** Выписка показывает прошлое. Для бизнеса под контракт (госзаказ, крупный заказчик) важна будущая выручка по договору, а для сезонного — управленческая отчётность. Андеррайтер должен учитывать их, а не только обороты за прошлые месяцы.

**Как встроить.**
- **A.** Запрос документов (S4.4) получает тип документа: `CONTRACT`, `MANAGEMENT_REPORT`. Андеррайтер вносит в карточке параметры контракта: заказчик, сумма, срок, график оплат. Пересчёт решения — тем же путём, что проверка условий (S5.4), с отметкой в истории, на основании какого документа.
- **B.** Мок реестра госконтрактов: по номеру — заказчик, сумма, этапы оплаты. Проверка, что заказчик из договора платит компании по выписке. Позже — извлечение реквизитов договора через OCR (S4.8).
- **C.** Новый вход `decide`: подтверждённая будущая выручка. Она добавляется к денежному потоку с дисконтом по надёжности заказчика. Управленческая отчётность (ОПиУ, ДДС) заменяет упрощение «денежный поток = 20 % оборота» — оно описано в [README скоринга](../../services/scoring/README.md).
- **D.** В карточке банка — блок «Контракты и отчётность» с введёнными параметрами и влиянием на лимит и DSCR. Клиенту — пояснение в запросе документов, зачем нужен договор.

**Почему не сейчас.** Нужны синтетические договоры и отчётность, согласованные с выпиской, и правила дисконтирования будущей выручки. Без них учёт контракта превращается в ручную правку лимита.

## Если делать дальше

Порядок по ценности для клиента и связям между историями:

1. **S2.2** — дёшево: продолжает предоценку и отказ, данные уже есть в скоринге.
2. **S5.5** — продолжает запрос документов (S4.4) и проверку условий (S5.4).
3. **S6.4** — после S2.2: альтернатива нужна там, где советов недостаточно.
4. **S3.6** — самая крупная. Меняет модель данных и контракты всех областей.
5. **S8.2, S4.8, S1.3** — когда понадобятся продуктам.
